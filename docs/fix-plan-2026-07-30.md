# Fix plan — from the 29 July product testing report

Ordered plan covering every finding in `product-testing-report-2026-07-29.md`. Ordering optimises for correctness first, then the product-defining work, then polish — not for implementation speed. Each phase lands with its own tests; nothing is batched so large it can't be reviewed properly.

Decision points that need Tom's call are marked **[DECISION]** and summarised at the end.

---

## Phase 0 — regression tests that should have caught what testing found

Write these first, failing where the bug exists, so every later fix flips a red test green.

1. **E2e: pagination exhaustion.** Seed 45+ photos, scroll to the end, assert every photo id appears exactly once and the end-of-feed marker is shown. Add a variant that fires two load-more triggers in the same tick (dispatch scroll + resize together) to reproduce the race deterministically.
2. **WebKit e2e: modal keyboard containment.** For every modal (name settings, color picker, upload, confirm dialogs, invite): Tab/Shift-Tab from every starting position stays inside the dialog and reaches Save/Cancel. Must run under the WebKit project since Chromium tab semantics can't reproduce the escape.
3. **E2e: corrupt-file selection** shows a specific inline error at selection time, before Upload is enabled.
4. **Unit: tombstone rendering rules** for comment threads (see 1.5).
5. **Unit: reaction pill ordering stability** while the picker/pointer is engaged (see 1.6).

## Phase 1 — correctness bugs

### 1.1 Pagination single-flight + offset integrity (report B1)
- Replace the `loadingMore` state guard with a ref-held in-flight promise; concurrent triggers await the same request instead of issuing a second one.
- Advance the offset exactly once per response, keyed to the offset actually requested (compare-and-set), so even a future double-fire cannot skip rows.
- **[TECH, recommended]** Replace offset paging with cursor paging (`uploaded_at, id` keyset). Offset paging over a newest-first list is inherently racy with concurrent uploads — the existing dedup/comment in the code is fighting the symptom. Cursor paging removes the whole class, simplifies `loadMorePhotos`, and matches D1/SQLite well. Backend keeps the offset endpoint until the frontend migrates (wire-type change in @photodrop/common).
- Add an explicit end-of-feed state ("You're all caught up") so a stopped feed is visibly complete rather than ambiguously truncated (report finding 27).

### 1.2 Focus trap rewrite for Safari (report B2)
- `useFocusTrap` intercepts **every** Tab/Shift-Tab while enabled and moves focus itself through its computed focusable list (respecting the trap's own order), instead of only intercepting at the boundary elements. This makes tab order identical across browsers regardless of Safari's "buttons aren't tabbable" default.
- Keep the existing "pull focus back in when it sits outside the container" behaviour.
- Audit initial-focus and focus-restore for every overlay while in there (lightbox already restores correctly).

### 1.3 Reaction attribution: replace hover tooltip with a real surface (report B3 + A3)
- Clicking/keyboard-activating the reaction summary opens a small popover listing who reacted with what (grouped by emoji). Kills the clipped tooltip bug and gives keyboard/AT users an equal path.
- Hover tooltip can stay as a shortcut, repositioned with collision-aware placement (flip below when near the top edge).

### 1.4 Client-side image validation at selection time (report B4)
- On file selection, decode the file (`createImageBitmap`, falling back to an `Image` load) before enabling Upload. Failure → specific inline error ("This file doesn't appear to be a valid image"), no broken preview, input reset.
- Distinct copy for HEIC-conversion failure (already exists) vs undecodable file vs oversized file.
- Surface backend rejection reasons verbatim instead of collapsing everything to "Upload failed" (the API already returns specific messages).

### 1.5 Tombstone rules (report B5)
- Render "This comment has been deleted" only when it preserves context: i.e. the thread has at least one visible comment. A thread whose comments are all deleted renders the empty state, and the badge count (already excluding tombstones) stays consistent with the panel.

### 1.6 Stable reaction pill ordering (report B6)
- Freeze pill order while the pointer is inside the pill row / picker is open; re-sort on mouse-leave/close. Toggling a reaction must not move targets under the cursor mid-interaction.

## Phase 2 — feed freshness (the product-defining fix; report G1)

Staged so each step is independently right:

1. **Cheap freshness probe.** Lightweight `GET /photos/latest` (newest id/timestamp + counts version, ETag'd). Frontend re-checks on window focus/visibilitychange, on navigation back to the feed, and on an interval while visible (~30–60s). If stale: fetch deltas and merge — new photos slide in at the top (with a "3 new photos" pill if the user is mid-scroll, to avoid content shifting under them); reaction/comment counts refresh in place.
2. **Mutation-driven refresh.** After the user's own mutations (display-name change, upload from another tab), invalidate the relevant caches so the visible feed reflects them immediately (fixes report U4's stale-byline half).
3. **[DECISION] True realtime (optional third step).** On Cloudflare, live push means either SSE from a Worker with polling underneath, or a Durable Object per group fanning out websocket events. A group-scoped Durable Object is the architecturally right answer if we want typing-indicator-grade liveness, but it's new infrastructure with real cost/complexity. Recommendation: land 1+2 (which make the app *feel* live for its usage pattern — families checking in), and take a separate decision on Durable Objects once that's in use.
- Pull-to-refresh stays as-is on touch; desktop additionally gets the focus/interval behaviour so there is always a refresh path.

## Phase 3 — upload overhaul (report G2, U7, part of B4)

- Multi-select (`multiple` on the input), drag-and-drop onto the feed/modal, and paste-from-clipboard.
- Upload queue UI: per-file thumbnail, per-file progress (compression stage + upload percentage via XHR/fetch progress), per-file failure with retry — one bad file must not sink the batch.
- **[DECISION] Captions in batch upload:** per-photo captions in the queue (recommended: optional caption field on each row, collapsed by default) vs a single shared caption vs captions only editable after posting (requires 5.3). Recommendation: per-photo optional captions.
- Preserve the existing pipeline per file (HEIC → JPEG, client compression, thumbnail generation); cap concurrent uploads (e.g. 3) to keep mobile memory sane.
- Server: existing rate limits reviewed so a legitimate 40-photo batch doesn't trip them.

## Phase 4 — engagement surfaces

### 4.1 Activity inbox (report G4)
- The bell becomes a true notification center: reverse-chron list of group activity relevant to you (new photos, reactions/comments on your photos, replies in threads you commented in), with unread dot + count, deep-linking into the lightbox at the right photo/comment.
- Backend: activity is derivable from existing tables (photos/reactions/comments + a per-user `last_seen_at`); no new event table needed initially. Wire types in @photodrop/common.
- Push notifications toggle moves to the user menu ("Notification settings"), decoupling "the inbox" from "push on/off".
- **[SETTLED 2026-07-30]** Scope: current group only (inbox follows the group switcher). Mark-read: opening the panel clears the badge; rows keep an unread highlight until the panel closes. Events: new photos (coalesced per uploader burst), reactions on your photos (coalesced per photo), comments on your photos, replies in threads you commented in, plus membership events (joins and role changes). Own actions never appear. History window ~30 days, derived from existing tables plus a per-user `last_seen_at`.

### 4.2 View receipts (report G3)
- **[SETTLED 2026-07-30: ship, visible to all admins, never to members.]** This matches the backend exactly as built (`requireAdmin` on GET /photos/:id/viewers) — no permission-model change needed. Since only admins can upload, every uploader can see receipts on their photos.
- Record views only on lightbox open (not feed scroll), debounced per photo/user. "Seen by" surface lives in the lightbox for admins (e.g. under the reaction rail), listing members with view time.

## Phase 5 — admin, invites, identity

### 5.1 Pending invites (report G5)
- Members list gains a "Pending" section: email, invited-by, sent-at, expiry state, resend (rate-limited) and revoke actions. Backend already stores invite tokens; needs list/revoke endpoints + resend.
- Invite dialog validates email format inline and warns on inviting an existing member.

### 5.2 Account switching & sign-out safety (report U2)
- Opening a magic link while signed in as someone else: interstitial "You're signed in as X — continue as Y?" (continue = switch). Removes the silent session replacement.
- Sign out gets a lightweight confirm (single modal, matching existing confirm pattern) since recovery requires an email loop.

### 5.3 Caption editing (report G6)
- Uploader (and admins) can edit/remove a caption after upload; edited captions show an unobtrusive "edited" marker. `PATCH /photos/:id` with caption in schema; feed + lightbox update in place.
- Photo *replacement* stays out of scope deliberately (delete + re-upload is acceptable for a wrong photo; replacing bytes under existing reactions is semantically murky).

### 5.4 Identity consistency (report U4)
- One rule: wherever a user is shown *within a group context*, use the per-group display name — including the header avatar initials/menu ("Signed in as" keeps the canonical name alongside). Avatar initials derive from the same string the adjacent UI shows.

## Phase 6 — downloads, export, group lifecycle (report G7)

- **[SETTLED 2026-07-30: default no downloads, per-user override — i.e. keep the existing model.]** The existing per-membership `image_protection` flag (DEFAULT 1 = protected) already is this model: everyone starts protected, admins can unprotect specific members. The only change: members whose protection is off get a real **Download** button in the lightbox (full-size file) instead of merely un-blocked right-click on the rendered blob. Protected members keep the current soft-blocking and see no button. No group-level toggle.
- **Group export before deletion:** owner-triggered "Export group photos" producing a zip (Worker streams R2 objects; caption/uploader manifest included). Delete-group flow offers export first — closing the "irreversible delete with no export path" hole.
- **[TECH note]** Zip streaming on Workers has memory limits; likely implemented as a paced client-side downloader (fetch each photo sequentially into a zip in the browser) rather than a server-side zip. Same UX either way.

## Phase 7 — polish & perceived performance

1. **Lightbox caption + position** (report U1): caption displayed in the lightbox (comment-panel header on desktop, overlay line on mobile) and a "14 of 53" position indicator.
2. **Header affordances** (report U3): install button gets an explicit "Install" label (or moves into the user menu on desktop); bell becomes the inbox (4.1). Icon-only buttons keep visible tooltips.
3. **Install prompt timing** (report U5): show after engagement (e.g. second session or first photo viewed), platform-correct copy (Dock on macOS, home screen on iOS/Android), respect "Don't show again" across sessions (already stored).
4. **Image loading feel** (report U6): skeleton shimmer on placeholders; thumbnails cached via the service worker (Cache API keyed by photo id — the SW already scopes `/photos/:id/download`); optional tiny blurhash/dominant-colour placeholder stored at upload time so cards paint instantly with the right tone.
5. **Comment sort control a11y name** (report A2): accessible name ("Sort comments: oldest first") + it's a real listbox/menu pattern.
6. **Small copy/behaviour sweep:** upload success banner auto-dismiss timing, em-dash caption spacing glyph check, "Version: dev" row styling in the menu, whitespace-only caption trimmed server-side (parity with comments).
